# 11 審查與品管

真寻的 world.execute(me) 成片 13,017 幀；為了檢查，開發期間渲染了超過 16 萬幀影片和約 8,900 張靜態圖。**檢查用的渲染量是成片的十倍以上**，這就是高品質作品和抽卡作品的差別。

## 證據階梯

由便宜到昂貴，能用便宜的證據回答就不要用貴的（papermotion 的檢查階梯，加上本專案的工具）：

| 層級 | 工具 | 回答什麼 |
|---|---|---|
| 1. 數字 | `qa` 報告、探針數值 | 時間對不對、有沒有黑幀、響度、閃爍次數 |
| 2. 靜態圖 | `stills --at …` | 構圖、字體、顏色、這一幀成不成立 |
| 3. 聯絡表 | `sheet --every 1.5` | 整體節奏、風格一致、後半段有沒有變水 |
| 4. 轉場條 | `qa` 自動產生，剪接點前後每秒 10 幀 | 交接有沒有斷、有沒有一幀閃白；切點後的主體在不在眼睛原本看的地方（[08](08-motion.md) 的視線） |
| 5. 逐幀條 | 最快的動作附近每一幀 | 動作有沒有跳、模糊是否正確 |
| 6. 低畫質預覽 | `render --preview` | 加上時間後的感覺 |
| 7. 成品 | 完整 MP4，有聲音 | 一切 |

取樣的限制要記得：**取樣只能證明取樣的時間點有什麼**，中間的短暫事件可能被漏掉（Hypit）。所以轉場附近要密集取樣，全片要有一次完整播放。

實例（本專案範例 [song-to-mv](../examples/song-to-mv/REVIEW_LOG.md)）：第三層的聯絡表每秒一張，看起來完全正常；第四層的轉場條在 0:08.50 抓到兩格歌詞字擠成一團，第二層逐格放大才看清楚原因（字跟著移動中的鏡頭排）。同一輪也在第二層發現右欄 200 px 的編號被裁掉頂端——聯絡表的縮圖太小，看不出來。

## 自動檢查

```
node tools/studio.mjs qa projects/my-mv
```

產生 `qa/report.md` 與一組圖片：

| 檢查 | 標準 | 來源 |
|---|---|---|
| **閃爍** | 任一秒內大面積亮度來回 ≤ 3 次；紅色閃爍另外計算（WCAG 2.3.1 的一般閃爍與紅色閃爍近似） | Nyankomintsu、EGSECDA |
| 黑幀與白幀 | 非刻意的全黑、全白幀 | — |
| 亮度曲線 | 每幀平均亮度；一個鏡頭內亮度意外下降的地方 | Nyankomintsu 的「亮度棘輪」 |
| 響度 | −14 LUFS ±1；真峰值 ≤ −1 dBTP | mg-styles-15 |
| 音畫同步 | 成品音軌與原曲的偏移 | Nyankomintsu |
| 卡點偏差 | 每個剪接、音效離最近拍點幾幀 | guizang |
| 分鏡 | 覆蓋全曲、沒有重疊、鏡頭長度變化、交接欄位 | paint-mv、onetake |
| 歌詞 | 閱讀時間、行寬、版本控制裡沒有歌詞全文 | Nyankomintsu |
| 規格 | 長度、解析度、幀率、有音軌 | — |
| 聯絡表 | 每格標**時間與當下的歌詞** | Hypit |
| 頻譜圖、波形圖 | 給「聽不到」的代理看 | xilo、papermotion |

閃爍檢查是近似值。要上電視或做商業發行，請用專業的光敏檢測工具再測一次。

讀報告時，**「鏡頭內亮度跳動」要先看鏡頭怎麼切。** 品管用分鏡的鏡頭邊界判斷「在鏡頭內」。一個鏡頭裡其實換了好幾個畫面（例如副歌一小節換一種風格）時，把它拆成每段一個鏡頭，切點放在小節線上；剩下的警告才是真的意外。刻意的（例如紅色淹滿整個畫面）寫進 REVIEW_LOG 的「接受」表並說明理由。

## 光敏安全

真寻與穆阿蒂布的 world.execute(me) 都在說明欄頂端加了光敏警告，並寫出閃爍的時間範圍。規則（EGSECDA、Nyankomintsu）：

- 任一秒內大面積明暗來回 **≤ 3 次**。剪接也算；高對比的移動圖案掃過某個點也算。
- 約 130 BPM 時，八分音符閃爍（每秒 4.3 次）就太快了；四分音符最多連續 2 小節；150 BPM 以上用二分音符。
- 不要飽和紅色的全畫面閃爍。
- 頻閃元素小於畫面 10%；快速的高對比條紋或螺旋小於 25%。
- 連續快切之間亮度跳動小於 50%。
- **全畫面閃白只由一個地方負責**，其他效果不能自己閃。
- **製作中就按段落量測**，不要等到最後。

需要強烈閃爍時：片頭放 5 秒警告頁（Nyankomintsu 的做法是放在負的歌曲時間，警告頁本身不閃、只用灰階），說明欄與標題也寫上時間範圍。

## 獨立評審

**不要讓代理評自己的作品**。悬剑听泉的獨立評審代理沒有主代理的上下文，避免「自己給自己打分」；T8star-Aix 的說法是「不要讓模型既當裁判又當演員」。

本專案的 [`agents/studio-jury.md`](../agents/studio-jury.md) 是一個評審子代理，它要看什麼、交出什麼報告都寫在裡面。用法：「請 studio-jury 評審 projects/my-mv 的 out/xxx_preview.mp4」。

### 七個面向

| 面向 | 看什麼 |
|---|---|
| 概念與敘事 | 有沒有一句話的核心概念、母題、首尾呼應；是不是作品集式的堆疊 |
| 音畫同步 | 歌詞、拍點、音效是否對上；人聲是主事件 |
| 動態工藝 | 曲線、重量、轉場的延續、有沒有原地晃 |
| 構圖與字體 | 焦點、層次、留白、中文排版、手機尺寸可讀 |
| 風格與完成度 | 風格一致、質感、前後段品質一致 |
| 聲音 | 混音、音效的理由與密度、響度、靜默 |
| 技術 | 規格、黑幀、缺字、閃爍、鋸齒、色帶 |

### 錨點（取自 mg-styles-15 的評審量表）

| 分數 | 程度 |
|---|---|
| 5 | 學生作業 |
| 6 | 模板等級、剪映等級 |
| 7 | 扎實的專業水準 |
| 8 | 高端廣告公司 |
| 9 | 獎項入圍 |
| 10 | 世界最好 |

「大部分的第一版應該得 5–7 分，不要灌水。」悬剑听泉的 22 支片第一輪平均 6.95，兩輪修改後 7.81。本專案的預設門檻是**每個面向 ≥ 8**；練習作品可以放寬到 7.5。

### 多輪評審

Voxyz 的黑洞實驗室跑了一整晚的「3 輪 × 3 個代理」：兩個評審各列 9–10 個問題並標 P0／P1／P2，一個修正者負責修；每輪有主題（材質與介面 → 鏡頭、互動與科普 → 設計總監的出貨決定與效能）；P0 全部修完；意見不同時寫下理由；每輪前備份、每輪後截圖、修不好的就退回。

也可以請**另一個模型**交叉審查：plotome 讓 GPT 找錯，南辰燏炚讓 Gemini 理解音樂並檢查剪接。

## 你的回饋怎麼寫

路北路陈用 38 則訊息讓代理複刻一段介面動畫，整理出五個方法：

1. **提示詞寫標準，不寫做法**。
2. **回饋說現象；它把原因搞錯時當場糾正**。他說「原片有一種波紋般的整體移動，你這沒有」，代理修好了。下一輪代理改了卡片間距來湊欄數：症狀修好，原因錯了。他立刻糾正「不是間距的問題，是攝影機的問題」，才改對焦距。
3. **看不清楚的，就畫出來、報幀號**：「原片 760–785 幀，所有波峰一樣高，只是鏡頭往右移」。幀號加上你對原理的理解，代理就不用猜。
4. **滿意了就凍結方向，先存基線**：git 打標籤，修正在分支上做，隔天確認後再合併。
5. **看不出差別就做對比頁；效果不好就退回**。他做了三個實驗，最後都退回基線：「實驗證明基線是對的」。

另外兩條：

- **說清楚不要什麼，那也是需求**（例如：不要片頭的黑底工作室 Logo）。
- **給量的參考**：「高一點」常常會變成太高。

可以直接用的句型在 [`prompts/zh-TW/revisions.md`](../prompts/zh-TW/revisions.md#回饋的句型)。

整理成**按場景的提示日誌**很有用（yym8224961 的 ASCII MV 公開了 25 輪）：每輪寫 `場景：mm:ss.s–mm:ss.s`、哪裡不對、方向。完成後再請代理寫一份「從零描述這個成品」的綜合提示。

## REVIEW_LOG.md

每一輪的分數、問題和處理寫進 `REVIEW_LOG.md`，範本在 [`templates/common/REVIEW_LOG.md`](../templates/common/REVIEW_LOG.md)。

## 風險項目的自我檢查

Nyankomintsu 的交接簡報有一節「風險項目自我檢查」，每一項都寫：

- 要渲染哪幾張靜態圖
- 明確的通過標準
- 明確的**退路**（做不到時改用什麼）
- 交付時寫出結論並附圖

例如：「高潮最後一幀：完整圖像對齊、全片最亮、靜止 1.2 秒以上。不通過時：改用 B 方案的構圖。」

## 誠實的交付報告

LCSlates 的馬賽克短片貼出了代理的交付報告，是很好的格式：附時間碼的場景清單、「逐幀看過後做的修改」（魚改色以和金色牆面區分、魚群更緊、反光調暗、對比、螺旋速度）、以及「仍然粗糙的地方」。

Tz_2022 的代理交接時寫：聽不到聲音、檢查了什麼、什麼應該是同步的、請你聽一次、哪裡可能不自然、因為畫面是決定性的所以可以用同一份素材重渲染直式版。

**交付報告要包含**：做了什麼、怎麼驗證的、沒有驗證的（特別是聲音）、已知的粗糙處、可以怎麼延伸。

## 常見失敗

交付前找一次（lemo-opuscar 的「最常見失敗」、Pip 短片的「已知失敗清單」）：

- 主體太小、太遠、或在畫面邊緣
- 太暗，或同色疊同色
- 字幕或歌詞蓋住主體或臉
- 笑點或重點太快，來不及看
- 角色走樣（和設定表不一致）

其他常見的（缺字、轉場閃白、特效脫離主體、後半段變水）原因與解法在 [16](16-pitfalls.md)，評審當成致命缺陷的列在 [`agents/studio-jury.md`](../agents/studio-jury.md)。
