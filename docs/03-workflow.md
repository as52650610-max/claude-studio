# 03 製作流程與關卡

一句話丟給 Opus 也能出片，但那是抽卡。把高收藏作品的做法攤開來看，共同點是**關卡**：在幾個關鍵時刻停下來確認，確認過的東西就凍結，之後只往前走。plotome 研究 Kurzgesagt、3Blue1Brown、影視颶風的製作流程後得出的結論是：代理可以扮演幾乎所有角色，只要人守住關卡。

本專案把各家流程（plotome 六道審查、lemo-opuscar、paint-mv、haiy、OpusClip、Pip 短片提示、Hypit）合併成八道關卡：

```
G0 簡報 → G1 時間鎖定 → G2 企劃與風格凍結 → G3 分鏡 → G4 樣片 → G5 製作 → G6 審查 → G7 交付
```

這一章講每一關為什麼存在、你要決定什麼。代理每一關的步驟寫在 [studio 技能](../skills/studio/SKILL.md)。

## 專案資料夾

`node tools/studio.mjs new projects/<名稱>` 建立的資料夾長這樣。每個檔案只負責一種事實，改東西時改「擁有那個事實的檔案」。

```
projects/my-mv/
├─ BRIEF.md          你的目標與只有你能決定的事（引用你的原話）
├─ TREATMENT.md      導演的答案：先想的點子、概念、母題、結構、風格、聲音方向
├─ STORYBOARD.md     分鏡表：每一鏡的時間、歌詞、畫面、鏡頭、卡點、交接、聲音
├─ PROGRESS.md       現在做到哪、下一步、偏離簡報的地方與理由
├─ REVIEW_LOG.md     每一輪審查的分數、問題、修正
├─ CREDITS.md        所有素材、字型、音樂的出處與授權
├─ film.html         影片本體（瀏覽器打開就能預覽）
├─ shots/            每一鏡或每一章一個檔案
├─ engine/           建立專案時複製進來的引擎（專案自己擁有，版本固定）
├─ frames/           其他工具做的畫面，存成編號圖片（studio frames 產生）
├─ data/
│  ├─ songmap.json   節拍地圖（工具產生）
│  ├─ lyrics.json    對齊後的歌詞時間
│  └─ cues.json      所有不在拍點上的時間點，一行一個，人工校正只改這裡
├─ audio/            歌曲、分軌、音效、混音（不進版本控制）
├─ qa/               聯絡表、轉場條、頻譜圖、品管報告
└─ out/              渲染輸出（不進版本控制）
```

| 什麼變了 | 改哪裡 |
|---|---|
| 目標、片長、平台、預算變了 | `BRIEF.md` |
| 設計方向錯了（概念、風格、結構） | `TREATMENT.md`，必要時重做 G3 |
| 某一鏡的內容或時間錯了 | `STORYBOARD.md` 和對應的 `shots/` |
| 某個字唱的時間不對 | `data/cues.json` 或 `data/lyrics.json`，不要在鏡頭程式裡寫死數字 |
| 你重複說了兩次以上的修正 | 寫進 `BRIEF.md` 的「長期規則」段落 |

最後一條很重要。可爱归归的 Undertale MV 被觀眾吐槽靈魂會「瞬移」，他把這條寫進全域規則，之後每次修改都會遵守。路北路陈也一樣：「前進的是鏡頭，不是檔案」這句回饋寫進規則檔後，撐過了 8 次上下文壓縮。

兩個範例的文件都是填好的，可以對照：[examples/hello-beat](../examples/hello-beat/)（27 秒、4 個鏡頭，最小的完整流程）與 [examples/song-to-mv](../examples/song-to-mv/)（35 秒、有歌詞、六章，全自動模式從 G0 走到 G7 前；它的 REVIEW_LOG 記下了每個被抓到的問題、怎麼修、哪些刻意保留）。

## G0 簡報

**目的**：一次問清楚只有你能回答的事，之後不再中斷。

代理在這一關**只發一則訊息問完所有問題**（lemo-opuscar 的做法）。好問題的標準是「答案會改變計畫」：xilo 的規則是最多 3 題，每題附預設值；风之谷AI 的提示是「開始前先問我 4 個決定性的問題」。

其中一題是**會不會公開**。私下練習的片可以用任何歌，歌和歌詞留在 `projects/` 裡、不進版控，版權的問題就跳過；要公開才需要回答權利（見 [13](13-rights.md)）。答案寫進 `BRIEF.md`（範本在 [`templates/common/BRIEF.md`](../templates/common/BRIEF.md)）。

**通過條件**：規格與預算都有答案；要公開的片，版權狀態也要有答案。不確定的地方寫「未知」，不要猜。

## G1 時間鎖定

**目的**：讓所有人（代理、子代理、你）都用同一個時間基準。時間錯了，後面每一鏡都要重做。

1. 分析器從歌曲量出 `data/songmap.json`（拍、小節、段落、停頓、重擊、鼓與人聲的事件、能量曲線），同時產生**點擊預覽音軌**：歌曲疊上節拍器，每個段落開頭響一聲鈴。
2. **你戴耳機聽一次**：拍子有沒有對上、第一拍是不是在正確的位置、鈴聲是不是落在段落真正開始的小節。不對的地方告訴代理，它會照你聽到的重跑（見 [04](04-music-timing.md#歧義工具要報告不能默默選)）。
3. 工具回報的歧義要處理，不要讓代理默默選一個。
4. 歌詞：拿到**官方歌詞文本**，對齊後逐句校對（見 [05](05-lyrics.md)）。
5. 所有不在拍點上的時間（某個字、某一聲鼓、某個特效）都寫進 `data/cues.json`，一行一個，標明來源。

**通過條件**：你聽過點擊預覽並確認；每一句歌詞都有開始與結束時間；歧義已解決或明確記錄。

> 為什麼要人聽？代理聽不到聲音。它能算出數字，但「這一拍其實是反拍」這種事，人耳一秒就聽出來。

## G2 企劃與風格凍結

**目的**：在寫任何鏡頭程式之前，把「這支片在說什麼、長什麼樣、聽起來像什麼」定下來。

### 先自己想，再看參考

研究、範例和風格卡是輔助，不是起點。代理看過什麼就會用什麼：papermotion 的範本刻意不附範例影片，因為代理讀過別人的短片就會重用它們的角色和橋段（[01 第 10 條](01-overview.md)）。從參考找來的樣子，最後會彼此相像。所以 G2 照這個順序：

1. **先想。** 打開 `styles/`、[案例](15-cases.md)或任何人的片之前，代理只根據 BRIEF 和素材（歌、歌詞、腳本），在 `TREATMENT.md` 的「先想的（First ideas）」寫下幾個自己的點子：這支片由什麼世界或材料構成、顏色的邏輯、一個動態的想法、一句話概念。粗糙沒關係，寫好幾個，之後也不刪，留著對照。
2. **再用參考把點子變具體**，不是用參考找點子。先用你放在 `refs/` 的素材，再找 AI 影片以外的東西：攝影、印刷品、電影、地方、你自己的生活。別人的 AI 片只拿來檢查有沒有撞。
3. **風格卡是選項，不是菜單。** `styles/` 的六張都是已經有名字的傳統。B 方案不能是現成的卡；哪個方案用了卡，要寫出這支片在卡上加了什麼。你在 G0 指定了卡就照你的，這時「先想的」寫的是這支片要加什麼。
4. **最後對照**「預設 Opus 風」清單（[07](07-style.md)）和下面的「不是再做一次範例」規則。

### 三個結構候選

lemo-opuscar 的導演規則說：一種風格的第一個點子，通常就是那種風格的陳腔濫調。所以 `TREATMENT.md` 先列**三個真正不同的結構**，再選一個並寫出理由。xilo 的三方案分法很好用：

| 方案 | 方向 |
|---|---|
| A 穩健 | 最貼近素材與歌詞字面意思 |
| B 新視覺語言 | 換一種媒材或風格來講同一件事 |
| C 大膽結構 | 一個貫穿全片的主角、一鏡到底、倒敘、單一隱喻 |

三個方案都從「先想的」長出來，每個方案要寫的欄位在 `TREATMENT.md` 範本裡。可以的話，每個方案附一張**用真程式渲染的靜態圖**，不要用色塊佔位。

技術路線要寫到每一鏡由誰畫：引擎、別的工具做的圖層，或整支片在別的工具做（[10](10-render.md#其他工具做的畫面)）。要啟動、安裝或付費的工具（Blender、ComfyUI、付費生成），你同意才用。

### TREATMENT.md 必須寫出

- **一句話概念**（conceit）：例如「一個聊天視窗就是她的全部世界」。
- **母題**（motif）：一個貫穿全片、會隨段落變化的元素。例如 mexicat P(doom) MV 的火花、Pdoom 動畫版每段副歌重複的指向手勢。
- **首尾呼應**：第一個畫面和最後一個畫面的關係（相同、反轉、拉遠揭示）。
- **能量曲線**：每個段落的強度（0–10），剪輯密度跟著曲線走。
- **克制預算**：每段要省掉什麼。《千本櫻》被批評「堆料太多沒有中心」，就是沒有這一項。
- **調色、字型、動態語法、轉場語法**（整支片只用 2–3 種轉場）。
- **聲音方向**：曲風或音色、哪裡要靜音。plotome 說他最大的遺憾是太晚決定音樂方向。

### 風格凍結

- 用真程式渲染 **2–3 張風格幀**，或一張**定調幀**（Lala罐頭 的說法：最能代表整支片氛圍的一格畫面，加一句為什麼）。
- 有角色就做**角色設定表**：正面／側面／背面、3–4 種表情、2–3 個關鍵姿勢、色票。並排放在參考圖旁邊，直到你說「對，就是他」（Pip 短片提示的做法）。角色定案後，改角色只要改一張圖；之後才改，每一鏡都要重做。
- 參考別人的作品時，用 lemo-opuscar 的「不是再做一次範例」規則：結構、開場、招牌鏡頭、運鏡路徑、配樂形狀、結尾，這六項至少四項要和參考不同。

**通過條件**：你從三個方案選了一個；風格幀或定調幀你看過並同意；角色（如果有）定案。

## G3 分鏡

**目的**：把整首歌鋪滿鏡頭，每一鏡都知道自己為什麼存在、怎麼交棒給下一鏡。

`STORYBOARD.md` 的分鏡表格式：

| # | 時間 | 歌詞／旁白 | 畫面（誰做什麼） | 鏡頭 | 卡點 | Out（交接） | 聲音 |
|---|---|---|---|---|---|---|---|
| 01 | 0:00.00–0:04.21 | （前奏） | 黑底上一個游標閃爍 | 固定，緩推 1.03× | 第 1 小節強拍游標出現 | 游標開始打字，字變成下一鏡的標題 | 底噪＋第一聲鍵盤 |

規則（來自 paint-mv、onetake、lemo-opuscar）：

- 分鏡表要**鋪滿整首歌**，不能有空檔；`studio plan` 會檢查。
- 一句歌詞大約一鏡，1.4–4 秒；超過 4 秒的句子可以拆。
- **鏡頭長度要有變化**：最長和最短至少差 4 倍。所有鏡頭一樣長，看起來就像投影片。
- **Out 欄位必填**：上一鏡留下什麼（形狀、顏色、物件、運動方向），下一鏡怎麼接住它。
- 卡點欄位寫清楚「哪個動作落在哪一拍」，時間用小節與拍表示（例：`T(17,1)`），不要寫死秒數。
- 至少留 2 處真正的「呼吸」：完全靜止或安靜的片刻，讓高潮有對比。

另外做 **4 張關鍵靜態圖**：開場、第一段副歌、高潮、結尾。

**通過條件**：`studio plan` 沒有 FAIL；4 張靜態圖你看過。全自動模式可以跳過人工核准，但檔案照樣要寫。

## G4 樣片

**目的**：在花大錢做全片之前，證明這個方向做得出來。

- 挑**最難、最有代表性**的一段做 10–15 秒，**要有聲音**。
- plotome 的教訓：「第一天就測最難的鏡頭」。他用 three.js 做了兩天原型，質感不夠，才換到 Blender。
- 汤姆CC 的做法：調風格時不要渲染整支片，先做 10 秒左右的版本確認視覺方案。
- 片子裡有別的工具做的鏡頭時，樣片要包含一鏡。
- 樣片通過後，請代理把風格整理成**可重用的規則**（寫進 `TREATMENT.md` 的風格段落），之後的每一鏡都照這份規則做。

**通過條件**：你看過、聽過樣片，對畫面、動態、卡點都滿意。不滿意就在這裡改，改到滿意為止，這是全流程最便宜的修改時機。

## G5 製作

**目的**：照分鏡把全片做出來，而且後半段的品質要和開頭一樣。

### 分章節

- 把歌曲切成 **8–25 秒的章節**，邊界放在段落起點（paint-mv 的做法）。
- 長片的後半段會退化（見 [01](01-overview.md) 原則 6）。對策：
  - 每一章用乾淨的上下文做，或交給平行子代理。
  - 所有章節共用一份**合約**：引擎、調色、角色函式、字型、共用元件、時間 API。
  - 審查後半段和開場一樣嚴格。

### 平行子代理（大型製作）

P(doom) 的作者讓主執行緒開 7 個子代理平行寫每一場戲；《三千年夜》用了約 80 個子代理。這樣做的前提是規則清楚：

1. 每個子代理**只改自己的章節檔案**。引擎改動交給主代理。
2. 開工前讀分鏡表，包括**上一章的最後一鏡與下一章的第一鏡**。
3. 每一鏡做完渲染聯絡表，**真的打開圖片看**。
4. 單幀最慢渲染時間有上限（例如 4 秒），超過要優化。
5. 中斷的子代理要**接續**，不要重新派發。

### 整合檢查

所有章節完成後，在每個章節交界的 **−0.1／0／+0.05／+0.3 秒**各取一幀，檢查：交接有沒有斷、歌詞有沒有蓋住臉、有沒有一幀閃白或閃黑。

### 進度紀錄

每完成一章，`PROGRESS.md` 加一行：完成了什麼、偏離了分鏡的哪裡與理由、還沒做什麼。這讓下一個對話（或下一個子代理）能直接接手。

## G6 審查

**目的**：用證據找出問題、排優先順序、修到過門檻為止。詳見 [11 審查與品管](11-review.md)。

1. **自動品管**（`studio qa`）：閃爍、亮度、響度、卡點偏差、字幕閱讀時間、黑幀。
2. **獨立評審**：派一個沒有製作上下文的評審代理，依七個面向打分（見 [11](11-review.md#獨立評審)）。悬剑听泉的經驗是，讓代理評自己的作品會手軟。
3. **你的筆記**：說你看到的現象，附時間或幀號（見 [11](11-review.md) 的回饋寫法）。
4. 問題分級：**P0** 必修（錯字、版權、閃爍超標、黑幀、不同步）；**P1** 影響品質；**P2** 有空再修。
5. 每一輪只修一類問題；修之前存基線，修完比對；沒變好就退回基線，並重新檢討原因。

## G7 交付

**目的**：交出可以直接發布的檔案，以及讓你日後能修改、能重現的一切。

`studio deliver` 一次做完字型、歌詞檢查、混音、渲染、品管、字幕、封面和交付說明（檔案清單見 [10](10-render.md#交付清單)）。代理另外寫 `CREDITS.md`（所有素材的出處與授權、AI 使用聲明）和 `REPRODUCE.md`（交給別的代理也能從零做出來的步驟）。

**完成的定義是「看過」**：完整播放最終的 MP4（不是預覽頁），有聲音。代理聽不到聲音時要明說「未經人耳確認」，並請你聽一次。發布按鈕永遠由你按。

## 協作模式與全自動模式

| | 協作模式（預設） | 全自動模式 |
|---|---|---|
| 適合 | 重要作品、第一次做、有明確想法 | 練習、快速試做、你信任代理的品味 |
| 停下來等你 | G0、G1、G2、G3、G4、G7 | 只有 G0（問一次）與 G7 |
| 檔案 | 全部要寫 | 全部要寫 |
| 一定要停的情況 | — | 要花錢的生成、版權問題、預算快用完 |

全自動模式的提示寫法：「問完 G0 的問題後一路做到底，中間不要停；每一關的檔案照樣寫；遇到付費或版權問題才停下來問我。」

## 付費生成的關卡

使用圖像、影片、TTS 等付費服務時（路線 R5），在第一次付費前，代理必須列出：

- 完整的分段製作腳本（每段時長、畫面、鏡頭、台詞、畫面文字、參考圖的角色）
- 模型與版本、每段長度、段數、**付費請求次數**、預估費用與上限
- 預留的重抽次數

你同意後才開始。規則：保存每次請求的收據以便續傳；**逾時不等於失敗，不能盲目重送**；已完成的素材不因本機錯誤而重生成（makevoid、OpusClip 的紀律）。

## 跨對話接手

長製作一定會跨很多個對話。每個新對話開頭：

1. 先讀 `PROGRESS.md`、`BRIEF.md` 的長期規則，再讀需要的檔案。
2. 不要重做已完成的步驟。
3. 結束前更新 `PROGRESS.md`。
